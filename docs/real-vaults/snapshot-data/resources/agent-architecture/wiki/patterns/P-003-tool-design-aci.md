# 问题
agent 的能力上限由工具设计决定，同样的模型、不同的工具接口，成功率天差地别。Anthropic 自述：做 SWE-bench 编码 agent 时，**花在优化工具上的时间超过花在整体 prompt 上的时间**。

# 法则（S-001 Appendix 2 "Prompt engineering your tools"）

1. **格式贴近模型在互联网文本中自然见过的形态**：markdown 代码块优于 JSON 转义；整文件重写优于 diff——diff 要求模型先数对变更行数，这恰恰是它容易错的地方。
2. **消除格式开销**：不让模型数几千行、不做字符串转义、别把输出逼进死角（给足思考 token）。
3. **Poka-yoke 防呆**：改参数让错误难以发生。实测案例：把相对路径参数改成绝对路径后，20 次调用 0 次路径失败。
4. **工具文档像给初级工程师写**：示例用法、边界情况、与其他工具的区别——模型对工具的全部认知就来自这段描述。
5. **像重视 HCI 一样重视 ACI**：给工具接口投入同量级的设计与测试，用多组输入实测模型的误用模式并迭代。

# 推荐用法
- 造任何 agent 前先过这张清单：
  - [ ] 每个工具有示例调用
  - [ ] 参数名自解释，相似工具间边界清晰
  - [ ] 输出格式是模型"擅长写"的格式
  - [ ] 错误返回本身可行动（错误信息就是 prompt）
- 工具成功率低时，**先改工具再改 prompt**（与本卡标题互为因果）。

# 反面教训
- 让模型输出需要精确计数/对齐的格式（行号 diff、表格对齐）。
- 工具描述只有一句话，模型只能靠猜用法。
- 把报错原文直接扔回上下文而不压缩成可行动信息（联动 [[P-002-context-discipline]] 因子 9）。
