# 旗舰：Agent Transaction Ledger（副作用合同）

## 用户场景
Personal Agent 未来要发邮件、创建提醒、写文件、改工单、提交表单。真正危险的不是不会调工具，而是调用了一半失败后，系统不知道哪些动作已经发生、哪些能撤销、哪些只能补救。

## 最小功能
1. FastAPI 建 transaction / action_journal 两张表。
2. 定义 5 类动作：CLEAN / RESTORATIVE / TOMBSTONED / MITIGABLE / TERMINAL。
3. 每个 MCP tool 注册 reversibility_contract、snapshot_required、compensator。
4. Agent 执行前生成 transaction plan，不直接调用。
5. 执行第 N 步故障时，按逆序补偿前 N-1 步。
6. TERMINAL 动作默认必须 human gate。
7. 生成 receipt：实际动作、补偿结果、未恢复副作用、人工责任点。

## 对照组
- A：普通 sequential tool calls + try/except；
- B：Saga-style 手工 compensating actions；
- C：本实验的 typed reversibility ledger。
不拿"全 LLM 裸奔"当对照。

## 验收指标
- 50 条故障注入复合工作流；
- TERMINAL 未经审批执行 = 0；
- 可补偿动作恢复成功率；
- partial side effect 遗漏率；
- 平均附加延迟；
- 新 tool 声明 compensation contract 的额外成本；
- 人工能否仅凭 receipt 复原"发生了什么"。

## 最大未知因素
真正困难的不是数据库 rollback，而是第三方 SaaS 的现实语义：邮件发出不能收回，工单删除可能留审计记录，文件恢复可能覆盖别人并发修改。实验价值恰恰是逼系统承认这些不可逆边界。
