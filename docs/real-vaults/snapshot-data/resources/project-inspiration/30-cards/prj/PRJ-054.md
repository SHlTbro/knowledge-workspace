## 用户与痛点
有些用户愿望不是今天能做，但未来模型、工具、成本或法规变化后可能变得可行。普通 Agent 的处理方式通常只有两种：现在失败后结束，或者每天定时重试。后者会不断烧模型、重复同一个不可能任务，而且没有客观标准判断"世界是否发生了足以重试的变化"。

## 功能流
用户用自然语言描述 wish 并提供资源；系统先把 prose 解析成签名的 on-chain schema，避免未来执行时直接依赖模糊原话。如果当前 Agent 已经通过该 wish 的 capability test，就执行；否则 wish 进入独立隔离的资源 cell，保持 dormant。每次主要模型能力更新后，系统重新运行 capability sweep；一旦公开 benchmark 首次满足预设条件，wish 被唤醒并执行。每个 capability run 有签名日志、pass/fail matrix 和可验证 attestation，资金/计算/API key 资源相互隔离。

## 真正机制
【作者公开】"re-tests itself against every major model release"是产品核心，capability sweep 作为公开证据。
【分析推断】真正可以搬走的是 Capability-triggered Retry：重试条件不是时间到了，而是先验阻塞条件发生变化。它适用于"当前模型做不到""某工具尚未支持""某 API 还没开放"的长期任务。

## 批判
最难的不是定时跑 benchmark，而是设计一个不会被模型"刷过"的 capability test。模型升级也可能在 benchmark 上通过、现实任务仍失败；资源长时间锁定还涉及机会成本和凭据过期。

## 迁移方向
Personal Agent 监听任务不要只设 cron。例如"等某招聘站支持稳定自动投递""等某模型能可靠处理 300 页合同"可保存 blocker predicate + benchmark。只有 capability test 从 FAIL→PASS 才唤醒。对照固定日重试，比较无效调用数、首次可执行发现延迟和误唤醒率。
