## 用户与痛点
MCP marketplace 可以列出很多服务，但"支持 swap""支持 research"这种自我声明没有办法告诉调用者：结果是否正确、工具路径是否乱跳、token 是否浪费、安全策略是否违规。

## 功能流
注册 MCP vendor → security gate 先检查 prompt injection、越权工具和 policy violation → golden benchmark 评 output correctness、tool-path correctness、token efficiency → evaluator 在 TEE 中运行并得到硬件签名 attestation → score + transcript hash 上链 → raw eval log 存内容寻址存储 → 其他 Agent 按 capability + threshold 发现服务 → 使用后按次支付。

## 真正机制
【作者公开】评测权重为输出正确性 45%、工具路径 35%、token efficiency 20%，安全门在评分前执行，一旦触发直接归零；TEE 评审使用硬件 attestation，评价历史被永久记录。作者还披露 CRE cron simulate 会挂，因此当前执行走 HTTP trigger。
【分析推断】这是 Verifiable Service Benchmark as Discovery Metadata：Agent 的 registry metadata 不只存"我会什么"，还要存"最近一次在什么 benchmark、什么版本、什么 judge 下做得怎样"。

## 批判
TEE 只能证明指定 evaluator 确实运行过，不能证明 benchmark 本身公平，也不能阻止服务针对公开 benchmark 过拟合。三个维度的固定权重也不适合所有任务。

## 迁移方向
给 Skill 仓库做一个"Skill Reliability Card"：能力声明 + 最近验证版本 + golden tasks + tool-path correctness + 成本 + dangerous failure；新版本发布后旧评分自动过期，而不是一次评测终身荣誉。
