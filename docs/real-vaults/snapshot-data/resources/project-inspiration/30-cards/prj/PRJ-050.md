- 技术：Jac + Python AST + coverage.py + Gemini 2.5 Flash + MCP；作者报告 17 个单测。

## 用户与痛点
AI Coding 可以迅速增加代码量，但 coverage report 只是列出未测行数。一个从来没人调用的 helper 和被 37 个核心函数依赖的未测函数，在普通 coverage UI 里可能同样是"红色"。

## 功能流
Python repo + coverage.py report → AST 静态扫描函数和调用 → 构建 Jac call graph → 找出存在 missing lines 且至少一个 caller 的函数 → fully untested 优先，再按 caller count 排序 → Gemini Agent 只读 top findings 的函数源码和 caller → 输出 test priority + 理由。

## 真正机制
【作者公开】BlindSpot 不执行被扫描代码；其风险排序结合 untested_lines、fully_untested 和 incoming call edges；LLM 层只能通过两个 read-only tool 阅读内存里的 flagged functions/callers。作者公开承认早期 false call edges 和 Gemini 漏项，需要代码侧 retry/过滤。
【分析推断】关键不是"AI 帮你补测试"，而是 Structural Test Debt：测试债务应该乘以依赖传播半径，而不是只数覆盖率百分比。

## 批判
name-based call resolution 仍会制造静态图误边；动态 dispatch、decorator、reflection、framework callback 更难覆盖。caller count 也不等于业务重要度，生产版应叠加 runtime trace、变更频率和事故历史。

## 迁移方向
把测试优先级从"覆盖率最低文件"升级到"未覆盖 × 被依赖程度 × 最近改动 × 失败历史"。对照普通 coverage threshold，测同样新增 20 个测试能提前捕获多少真实 seeded defect。
