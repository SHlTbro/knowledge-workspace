## Aivy — 不要给一群 Agent 共用一个"上帝钱包"，每个 Agent 都应该是独立风险单元

**赛事/奖项：** Hello Future Apex 2026 AI & Agents Track 3rd，奖金 $8,000；GitHub jmgomezl/aivy（commit e95e50fa40，12 个 L2 源文件已钉）。

**功能流：** 部署 Agent → 为每个 Agent 创建独立 Hedera account → KMS 加密 Ed25519 私钥 → 部署 AivyVault → 合约层配置 spending cap → 按 capability group 分配 50+ Hedera tools → cron/链上事件触发 Agent → 全动作写入 HCS audit topic。

**源码验证的真实符号：**
- `contracts/AivyVault.sol`：`spendingCapTinybar` 链上额度；`logExecution()` 中 `require(amountTinybar <= spendingCapTinybar, "cap exceeded")` 硬约束；`paused` 可暂停；`updateGuardrails()` onlyOwner。
- `server/kms.ts`：`SHARED_KEY_ALIAS = 'alias/aivy-agent-keystore'`——**代码实际是一个共享 KMS 密钥**，所有 agent 私钥用同一密钥加密，通过 `EncryptionContext={platform, keyType, agentId}` 区分；`createAgentKmsKey()` 生成 Ed25519→KMS Encrypt→`privateKeyBytes.fill(0)` 擦除；`decryptAgentKey()` 解密后 `(decryptResult.Plaintext as Buffer).fill(0)`。
- `docs/KMS_SECURITY.md` 描述"each agent gets a dedicated KMS key"，**与代码实际的共享密钥设计不一致**——文档过时或不准确。
- Fallback：`isKmsConfigured()` 为 false 时降级到本地 AES-256-GCM（ECDSA 密钥），因此"始终由 KMS 保护"不能泛化。
- 三层安全模型：Layer1 Application(JWT+rate limit) → Layer2 AivyVault.sol(on-chain cap) → Layer3 AWS KMS。

**真正机制：** 【作者公开】每个 Agent 独立账户、KMS 加密、Vault contract 和 HCS audit topic；Compliance Clerk 可只获得 query capability，无法 mint token。【分析推断】把 Agent 从"软件线程"变成 Risk Principal：身份、钱、权限、审计都独立，可单独冻结和限额。

**批判：** 共享 KMS 密钥意味着若该密钥被攻破，所有 agent 私钥均可解密（EncryptionContext 是 AAD 不是独立密钥）；链上限额只能约束可表达的资金规则，无法阻止所有经济损失；fallback 模式下安全等级显著下降。
