## 用户与痛点
Tool-using Agent 的训练与评测需要大量 task→thought→tool call→observation→answer 轨迹，但普通 sandbox 只负责"收集"，然后把所有 rollout 一股脑扔进训练集。失败轨迹、循环调用、幻觉工具、重复行为和低信息量路径会污染数据。

## 功能流
seed task → Agent 在可插拔 sandbox 中线性/树状探索 → LLM Judge 做 goal/efficiency/coherence/tool-use 四轴评价 → 确定性规则过滤 parse error、tool error、重复循环、空回答 → top-N diverse selector 去重与多样性选择 → 对可挽救的低质量轨迹重新探索与修复 → 产出 training-grade trajectory dataset。

## 真正机制
【作者公开】明确把轨迹流水线拆成 Generate / Evaluate / Select / Filter / Refine；Selector 使用确定性深度、信息量、工具多样性权重和 Jaccard 去重，Filter 不是 LLM 判断。
【源码级】TrajectoryQualityEvaluator（OperatorABC）四轴评分各 1-5，输出 traj_goal_achievement/efficiency/coherence/tool_use/overall/rationale 列，ThreadPoolExecutor(max_workers=8) 并发，max_observation_chars=1500 截断。TrajectoryFilter 8 条 opt-in 确定性规则（require_success/min_steps/max_steps/drop_parse_errors/drop_invalid_tools/drop_tool_errors/max_repeated_actions/require_nonempty_answer），无 LLM 调用，重复动作检测用 Counter+(tool,json.dumps(args,sort_keys=True)) 作为 key。
【分析推断】最值得迁移的是"Agent Experience ETL"：Agent 的历史不是 Memory 就完事，而应像数据工程一样有质量门、去重、修复和版本边界。

## 批判
LLM-as-judge 仍可能把同源偏差带入训练数据；"修复失败轨迹"也可能把真实失败模式擦掉。好的系统应该同时保留 raw trajectory、quality metadata 和 refined trajectory，而不是只留下漂亮结果。

## 迁移方向
给 AI Coding workflow 建 Experience Distiller：每轮执行保留 task、tool path、失败类别、retry、review、最终验收；确定性过滤重复无效轨迹，再从"失败但有学习价值"的 run 生成训练/Skill 候选。验收不是"存了多少日志"，而是后续任务的重复失败率是否下降。
