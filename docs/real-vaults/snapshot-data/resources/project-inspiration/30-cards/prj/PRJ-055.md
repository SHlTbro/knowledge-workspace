## 用户与痛点
大多数 Coding Agent 接到需求后生成一条计划，沿这条路径改代码，遇到错误再修。如果最初的 architecture assumption 就错了，后续大量 token 都会用于修补同一个坏方向。

## 功能流
系统先提出多条候选 approach，不立即承诺其中一条；learned controller 决定哪些路径 expand、哪些 prune、哪些应该进入真实 test 验证。compiler error 和 failing test 不只是聊天文本，而会反向影响 controller 对路径的权重。IDE 内展示整个搜索过程，让工程师能看到哪些路被探索、为何被放弃。

## 真正机制
【JetBrains 官方公开】项目明确从 single-shot 改成 search-like reasoning，并使用 tests/compiler feedback 回流 controller。
【分析推断】可概括为 Branch-and-Verify Coding：推理资源不是在一条 chain 上无限加长，而是按证据动态分配给多个方案。它跟普通 best-of-N 的区别是失败证据会改变后续搜索，而不是 N 个答案最后投票。

## 批判
搜索会扩大成本；如果 controller 的 reward 只认短期 tests，就可能偏向"能过当前测试"的局部方案。复杂真实项目还需要 architecture-level invariants 和长期维护成本。

## 迁移方向
给 Coding Harness 做一个最小 Branch Challenger：复杂任务先生成 3 个互斥实现策略，每个只花固定预算做 feasibility probe（例如最小 patch + 单测），再让真实 build/test 分数决定哪个进入完整实现。对照单路线 high-thinking，测总 token、首次通过率和 architecture rewrite 次数。
