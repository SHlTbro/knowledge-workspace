## 项目证据
- 赛事：JetBrains × Codex Hackathon 2026，第三名。
- 官方介绍：https://blog.jetbrains.com/ai/2026/05/meet-the-finalists-jetbrains-codex-hackathon/
- 团队公开说明其实现为 MCP server；官方文章未给出可靠 canonical GitHub。

## 用户与痛点
Coding Agent 换一个 IDE、换一台电脑、换 Codex/Claude，项目上下文就重新冷启动。最笨的办法是把旧聊天全部塞给新 Agent，这会把 dead ends、过期 tool output、重复说明一起搬过去，context 越"完整"越像搬家时舍不得扔垃圾。

## 功能流
mesh-code 建立共享 project memory，持续记录 what's been tried、what's been decided、what's still pending。一次会话从 laptop A 开始，可以到 laptop B 继续；不同 Agent / provider 读取同一个中间状态。团队公开说明其 MCP 可以在 Codex、Claude 等不同 agent session 之间同步 context。

## 真正机制
【JetBrains 官方公开】重点是跨机器、跨 Agent 的 shared memory，不要求固定模型。
【团队公开】成员称它是 real-time context mesh，并强调跨 session / user / provider。
【分析推断】更值得迁移的是 Decision-state Memory，而不是 Transcript Memory：长期状态只保存决策、证据、未完成项和失败路径摘要，而不是保存每个 token。

## 批判
共享 memory 会把单 Agent 的错误放大成全团队错误；跨设备还要处理并发写、过期 decision、撤销和访问控制。Memory 不是越多越好，最难的是 lifecycle。

## 迁移方向
给本地 Agent 工程建立四类持久状态：DECISION、EVIDENCE、PENDING、REJECTED_PATH。新会话只加载当前有效状态与 source hash；旧的完整 transcript 留冷存储。比较"全聊天恢复"和"结构化状态恢复"的 token、错误重复率和 stale decision 使用率。
