## 用户与痛点
小团队没有 SOC，面对登录失败、MFA 拒绝、成功登录、MFA 被关闭、新 API key、数据导出等事件时，单条日志都看得懂，但难在判断这些事件是否属于同一个攻击链、哪些是事实、严重性多高。直接把日志喂给 LLM 会产生一个很危险的问题：叙事能力越强，越容易把不存在的因果关系写得像真的。

## 功能流
应用 SDK 采集原始 telemetry → deterministic investigation engine 根据规则生成 evidence / attack stages / initial risk → UEBA ensemble 只提供行为异常上下文与受限 score refinement → graph correlation 找结构相似的历史 incident → local LLM 在冻结后的 incident context 上生成 narrative、建议和问答。GitHub 明确规定：LLM 不能改变 evidence 或 risk score，UEBA 也不能独立创建 investigation。

## 真正机制
【作者公开】README 把层级边界写得很清楚：deterministic layer 是 authority，ML 是 bounded refinement，LLM 是 interpretation。
【源码级】UEBA 服务 FastAPI /score 端点：3 检测器 ensemble（isolationForest / ecod / copod），empirical_percentile 归一化，weighted_anomaly_score 加权；explain_top_reasons 用 median + MAD baseline 输出 top 3 feature reasons；validate_bundle 检查 9 个 required_keys（schemaVersion/modelVersion/featureNames/detectors/detectorWeights/scoreReferences/anomalyThreshold/featureBaselines）；schemaVersion 不匹配返回 503。
【分析推断】这是 Evidence-before-Narration / Authority Separation。生成模型最擅长解释，最不应该拥有"事实层写权限"。

## 批判
deterministic 并不等于正确，规则库自身可能漏攻击；合成数据训练的 UEBA 不等于真实企业分布；attack graph 相似也不能推出同一归因。它最成熟的不是检测指标，而是"谁有权改事实"的架构边界。

## 迁移方向
用在 RAG/Agent 审计：parser/test/tool output 写 Evidence Ledger；LLM 只能引用 evidence_id 解释或提出 hypothesis，不能直接把"可能"改成 VERIFIED。对照普通 LLM incident summary，注入 100 条无关但语义诱导很强的日志，测 unsupported causal claim rate。
