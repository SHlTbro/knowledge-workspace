# PH-001 可证性先于完备性：设计规则必须有"机验位"

## 一、设计观陈述

**写规则之前，先回答"它在哪里被证明生效"。** 一条设计规则的价值不取决于写得多周全，而取决于是否存在一个可机验、可留痕、可举证的检查位：能被 lint/探针/回执强制点名的规则才算落地；寄托在字段、自觉、口号上的规则等于没写。与此配套的两条推论纪律：**负结果也要留痕**（查不到、没发生也必须白纸黑字声明，堵死"假装做过"），**未验证的如实降级**（不承诺自己没验过的环境）。宁要少而可证的规则，不要多而悬空的规则——可证性优先于完备性。

## 二、三卡各自体现（到具体决策点）

### D-001（kb-operator）：权限约束必须有 lint 机验位，不寄托字段
- **决策点 §3.1（红线全部写进正文，非 allowed-tools）**：6 条红线写进 SKILL.md 正文并由 `vault-lint.sh` 机验，卡内明令"allowed-tools 不得作为权限边界"（溯源 `SKILL.md:32`）——因为 opencode 等客户端会静默忽略该字段，寄托在字段上的权限=无权限。这是"规则必须落在可执行检查位"的最直接体现。
- **决策点 §4.2（post-compaction 对策）**：关键状态全部外置到 vault 文件（REGISTRY/快照/提案），不依赖会话内存——生效证据要能脱离易失载体被事后复查。
- **决策点 §4.3（保真分级）**：四平台 verified、claude-code 仅 best-effort 并如实标 pending——没验过的环境不承诺，是"可证性"纪律的反面约束（禁止无证据的完备性宣称）。

### D-002（tdd-for-skills）：每条规则必须配"无规则时的失败实录"作为出生证
- **决策点 §二-E 步骤 1（RED）**：先派 agent **不加载 skill** 跑应触发场景，记录可复现的错误动作；产物被明确定义为"'无 skill 时会错在哪'的证据表"，证明"规则是被需求逼出来的"——规则的合法性来自可复现的失败证据，而非写作者的直觉完备性。
- **决策点 §二-E 步骤 2 判停（GREEN）**：需要 >5 条规则才能通过场景时，判停方向是"拆 skill 或场景选窄"，而不是继续堆规则——宁少勿滥、以可通过验证为界的直接体现。
- **决策点 §二-E 步骤 3（REFACTOR）**：压力矩阵选 ≥3 类绕过场景实测，每被绕过补一招并**重跑 GREEN 确认仍绿**——补规则本身也要过机验位，不允许"写了就当堵上了"。

### D-003（mandatory-kb-routing-gate）：流程口号升格为带判停的闸，负结果强制声明
- **决策点 §二-E 步骤 1（开工闸判停）**：开工回执必须点名消费的卡/skill，**查不到也必须写"已检索，无命中"——写不出来=没查，打回**。负结果强制留痕，把"查库"从口号变成可检查动作。
- **决策点 §二-E 步骤 2（评审闸判停）**：只贴 `#标签` 不列解决了哪个子问题=消费不成立——为"消费证据"设立真假判据，贴标签冒充消费被列为红线（溯源会话 `:265`"贴标签锚不合法"）。
- **决策点 §一（解决什么）**：卡内自述病灶=历届 agent 从未被强制检索、老卡零消费——正是"无检查位的制度无人执行"的反例，三闸是对该失效模式的制度性回应。

## 三、可操作推论（新 skill 设计时如何套用）

1. **逐条问机验位**：写下任何一条红线/规则时，同步回答"它由什么检查？"——lint 规则、行为探针场景、还是回执强制字段；三者都答不出的规则，要么删、要么降级为建议性表述并明示不可机验。
2. **先录失败再写规则**（D-002 移植）：新 skill 的每条实质规则，先取得"无此规则时 agent 实际犯错的实录"再动笔；没有 RED 证据的规则不进入正文。
3. **负结果声明制度化**（D-003 移植）：凡流程含检索/检查动作，产出物必须支持"无命中"声明位，且验收方以"写不出无命中声明=未执行"为判停。
4. **如实分级，拒绝悬空承诺**（D-001 移植）：对未实测的平台/环境/场景，用 fidelity 式分级标注（verified/pending/best-effort），禁止以完备性口吻宣称未验证能力。

## 四、边界（哪些场景不适用）

- **无行为可测的对象**：纯信息查询、纯文案类产出没有"生效/失效"二值可探，D-002 式行为探针不适用（D-002 §二-B 已自列此边界），此时"机验位"退化为人工评审清单，不应硬造探针。
- **平台能力缺失时**：机验位依赖平台真实能力（hook/lint/子 agent）；平台不支持时正确动作是**降级声明**（D-001 §4.2 已有先例），不是伪造检查或把约束静默寄托回字段。
- **一次性试验探查**：D-003 §二-B 明确一次性任务不适用三闸；对探索性工作强套机验位会制造形式主义勾选（D-003 §二-B 自列失败模式）。
- **可证性不等于唯机验**：本卡不主张"不能机验的规则一律删除"——不可机验但有价值的约束可以保留，条件是明示其不可机验属性，不冒充已落地。

## 五、V3 独特性检验：推导出的新设计建议（三卡原文均未明说）

1. **新建议 A——"机验位清单"应成为 skill 设计文档的必备交付物**：三卡各自拥有零散机验位（D-001 的 lint、D-002 的探针场景、D-003 的回执字段），但没有任何一卡要求把"规则→检查位"的映射本身汇总成一张可审计清单。推论：新 skill 入库时应随卡交付一张"每条实质规则 ↔ 其机验位（lint 条目/探针场景/回执字段/人工评审项）"对照表，清单中"无机验位"列非空的规则必须带显式豁免理由。此建议为三卡机制的归纳外推，非任一卡原文句。
2. **新建议 B——"无命中声明"机制可推广到设计决策本身**：D-003 的无命中强制声明只覆盖开工/评审/新需求三个流程时间点。推论：设计卡正文中凡出现"已考虑过 X 方案/已排查 Y 风险"类主张，都应能指回一次具体检索或检查动作留痕，指不出的视同未考虑——把"负结果举证责任"从流程闸推广到文档论断层。三卡均未提出此推广。
